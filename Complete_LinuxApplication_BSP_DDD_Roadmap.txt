1. Embedded & Hardware Fundamentals
---------------------------------------------------------------
	Microcontroller vs MPU vs SoC:
		- A Microcontroller Unit (MCU) is a self-contained single-chip computer with a processor, memory, and input/output peripherals designed for specific control tasks.
		- MPU (Microprocessor Unit) is just the CPU core that requires external memory chips.
		- System on a Chip (SoC) combines high-performance processing power with integrated memory and complex hardware accelerators to run full operating systems.

            | Feature              | Microcontroller (MCU)                                        | Microprocessor (MPU)                                              | System on a Chip (SoC)                                             |
            | -------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
            | **Main Definition**  | CPU + Flash/ROM + RAM + basic input/output on one chip.      | Only the CPU core; needs external RAM and storage.                | High-integration system with powerful cores, graphics, and memory. |
            | **Operating System** | Runs bare-metal code or a Real-Time Operating System (RTOS). | Runs rich operating systems like Linux.                           | Runs complex operating systems like Linux, Android, or iOS.        |
            | **Power Use**        | Very low power (microamps in sleep mode).                    | Higher power consumption.                                         | High power consumption due to high speeds.                         |
            | **Common Uses**      | Washing machines, sensors, car engine controls, IoT nodes.   | Industrial computers, gateways, and older single-board computers. | Smartphones, smart TVs, tablets, and advanced route                |

        - Microcontroller (MCU): Choose for dedicated, low-power, predictable tasks like reading sensors, controlling a motor, or running a simple digital display.
        - MPU (Microprocessor): Choose when your product needs heavy data processing, large external memory scalability, and standard high-level OS networking.
        - SoC (System-on-Chip): Choose for modern smart devices requiring advanced graphical interfaces, high-definition video, artificial intelligence acceleration, or wireless connectivity.
        
	CPU architecture: ARM Cortex-A/R/M:
        - ARM Cortex processor profiles (A, R, and M) are distinct architecture specifications designed for specific computing needs, ranging from high-performance operating systems to low-power microcontrollers.
        - Cortex-A (Application Profile)
            - Purpose: Designed for high-performance computing, heavy multitasking, and running rich operating systems.
            - Key Features: Includes a full Memory Management Unit (MMU) for virtual memory, support for complex multi-core clusters, and advanced SIMD extensions like Neon or SVE.
            - Operating Systems: Runs full-featured operating systems like Linux, Android, QNX, and Windows on Arm.
            - Common Uses: Smartphones, tablets, smart TVs, enterprise servers, and automotive infotainment systems.
        - Cortex-R (Real-Time Profile)
            - Purpose: Built for mission-critical systems requiring fast, highly deterministic, and predictable response times.
            - Key Features: Replaces the MMU with a Memory Protection Unit (MPU) and utilizes Tightly Coupled Memory (TCM) to ensure fixed execution and interrupt latencies without cache jitter.
            - Operating Systems: Runs specialized Real-Time Operating Systems (RTOS) or bare-metal code.
            - Common Uses: Automotive braking and powertrain control, industrial robotics, aerospace systems, and medical devices.
        - Cortex-M (Microcontroller Profile)
            - Purpose: Optimized for ultra-low power consumption, tiny silicon footprint, and deep embedded efficiency.
            - Key Features: Cacheless or minimal cache design, built-in Nested Vectored Interrupt Controller (NVIC) for low-latency interrupts, and optional hardware Floating Point Units (FPU).
            - Operating Systems: Runs bare-metal applications or lightweight RTOS (cannot run Linux or Windows due to the lack of an MMU).
            - Common Uses: Sensor nodes, smart meters, wearables, home appliances, microcontrollers (like STM32, Arduino, and Raspberry Pi Pico).

	Memory map and address spaces:
        - A memory address map is a layout that assigns specific address ranges to system components like RAM, ROM, and input/output (I/O) devices
        - What is an Address Space?
            - Address Spaces: The actual set of all physical addresses corresponding to hardware locations in the computer's main memory (RAM).
            - Logical (Virtual) Address Space: The abstract range of addresses generated by the CPU or a program, providing each process an independent view of memory.
            - Physical Address Space: The actual set of physical locations available in the computer's hardware RAM.


	ROM, SRAM, DRAM, NOR/NAND/eMMC/UFS
        - Semiconductor memory divides into volatile (power-dependent) and non-volatile (persistent) types, each designed for different tasks across computer systems.
        - Volatile Memory (RAM):
            1. ROM (Read-Only Memory): Non-volatile memory that stores permanent startup instructions and firmware (like a BIOS). Data remains saved even when power is turned off.
            2. SRAM (Static RAM): Extremely fast, low-latency memory that uses flip-flop circuits. It does not need constant refreshing, making it ideal for CPU cache, but it is expensive and has low density.
            3. DRAM (Dynamic RAM): Slower than SRAM but denser and cheaper. It stores bits in a capacitor that must be refreshed thousands of times per second. It serves as a device's main system memory.
        - Non-Volatile Flash Storage & Interfaces:
            1. NOR Flash: Offers fast read speeds and supports byte-level random access with Execute-in-Place (XIP) capability. It is used for storing boot code, but writing and erasing are slow and expensive.
            2. NAND Flash: Optimized for high density, lower cost per bit, and fast writing/erasing. It handles mass data storage but requires sequential or block-based access through a controller.
            3. eMMC (embedded MultiMediaCard): Integrates raw NAND flash memory with a basic controller into a single chip package. It uses a half-duplex interface common in budget smartphones and tablets.
            4. UFS (Universal Flash Storage): An advanced storage standard that supersedes eMMC. It supports full-duplex operation for simultaneous reading and writing, delivering much higher speeds for modern smartphones and high-performance mobile devices.

	Registers and bit manipulation:
        - Bit manipulation is the act of using bitwise operators to inspect, set, clear, or toggle individual bits inside hardware or CPU registers without changing the other bits..
    
	Interrupts and exceptions:
        - An interrupt is an asynchronous signal from external hardware requiring processor attention, whereas an exception is a synchronous event triggered internally by the CPU during instruction execution due to an error or special condition
        - Key Differences:
            - Source: Interrupts originate outside the CPU (e.g., I/O devices, timers), while exceptions originate from within the processor as a result of executing an instruction.
            - Timing: Interrupts are asynchronous and can happen at any time regardless of the running program; exceptions are synchronous and occur precisely at the instruction that caused the issue.
            - Purpose: Interrupts manage external real-time events, whereas exceptions handle programming errors or abnormal conditions like division by zero.
            - Handling: Interrupts are handled by an Interrupt Service Routine (ISR), while exceptions invoke an Exception Handler (which classifies them into faults, traps, or aborts).

	Clocks and reset architecture:
        - A robust clock and reset architecture ensures that a System-on-Chip (SoC) or digital circuit powers up, transitions states, and operates synchronously without timing failures or metastability.
        - Clock Architecture:
            - Clock Generation: Relies on crystal oscillators and Phase-Locked Loops (PLLs) to generate stable, high-frequency internal operational clocks from a reference input.
            - Clock Distribution: Uses a structured clock tree to minimize skew and propagation delay as the clock signal fans out to sequential elements across the chip.
            - Multiple Domains: Modern SoCs divide logic into distinct functional clock domains (e.g., high-speed processing, low-power peripheral, and interface clocks like APB or SPI) bridged safely via FIFOs or synchronizers.
        - Reset Architecture
            - Central Reset Controller: Gathers external signals (Power-On Reset, dedicated reset pins) and internal triggers (watchdog timers, PLL lock indicators) to orchestrate safe startup sequences.

	GPIO fundamentals:
        - General Purpose Input/Output (GPIO) pins are programmable digital signal pins on a microcontroller or processor that act as a bridge between internal software logic and the physical world.
        - Core Concepts:
            - Digital Signals: Operates using two basic voltage states—HIGH (logic 1, representing supply voltage like 3.3V or 5V) and LOW (logic 0, representing ground/0V).
            - Configurable Direction: Pins can be set via software to act as either an input or an output on a pin-by-pin basis.

	Timers and watchdogs:
        - A watchdog timer (WDT) is an electronic or software-based hardware counter that automatically resets a system if the software or firmware freezes, hangs, or stops responding

	DMA basics:
        - Direct Memory Access (DMA) is a system feature that allows hardware peripherals to transfer data directly to and from main memory without heavy involvement from the CPU.
        - Core Components of DMA:
            - DMA Controller (DMAC): A dedicated hardware chip or circuit that manages the data transfer channels and takes control of the system bus.
            - Address Register: Holds the target memory address for the read or write operation.
            - Word Count Register: Tracks the remaining number of words or bytes left to transfer.
            - Control Register: Specifies the transfer direction (read/write) and operational mode.

	Cache and MMU basics:
        - Cache memory and the Memory Management Unit (MMU) work together to speed up how a computer processor accesses and manages data.
        1. Cache Memory Basics: 
            - Definition: A tiny, extremely fast type of computer memory located close to the CPU core.
            - Purpose: It stores duplicates of frequently used data from the main memory (RAM) to reduce waiting time.
            - Levels: Divided into layers—L1 (smallest and fastest), L2 (larger and slightly slower), and L3 (shared across cores).
            - Hit vs. Miss: Finding data in the cache is a cache hit (fast), while missing it requires fetching from the slower RAM (cache miss).
        2. Memory Management Unit (MMU) Basics:
            - Definition: A hardware component that acts as a bridge between the CPU and RAM.
            - Address Translation: Converts virtual (logical) addresses generated by programs into actual physical addresses in RAM.
            - Virtual Memory & Paging: Splits memory into fixed-size chunks called pages to let programs run smoothly even if they exceed physical RAM size.
            - Memory Protection: Enforces security rules and permissions to stop programs from crashing or accessing unauthorized memory.
            - TLB: Contains a tiny internal cache called the Translation Lookaside Buffer to speed up address conversions by remembering recent translations.

	

2. Linux Fundamentals
---------------------------------------------------------------
	Linux boot process:
        - The Linux boot process follows a sequence of five main stages from the moment you turn on the power to the final login prompt.
        1. BIOS/UEFI Firmware
            - Power-On Self Test (POST): The system firmware checks core hardware like your RAM, keyboard, and storage drives.
            - Firmware execution: The BIOS or UEFI looks for a bootable storage device based on your set boot order.
            - Device loading: It reads either the Master Boot Record (MBR) or GUID Partition Table (GPT) to find the primary bootloader.
        2. Boot Loader (GRUB)
            - Menu display: The bootloader—most commonly GRUB 2—shows a menu allowing you to pick a kernel version or operating system.
            - Loading files: GRUB loads the compressed Linux kernel image and the temporary initramfs (initial RAM filesystem) into memory (RAM).
            - Handover: Control of the system passes directly to the Linux kernel.
        3. Kernel Initialization
            - Decompression: The kernel unpacks itself into memory and sets up core hardware drivers and memory management.
            - Temporary root: It mounts the initramfs as a temporary root file system to find essential storage drivers.
            - Real root: The kernel mounts your actual hard drive file system as the real root directory.
        4. Init System (systemd)
            - Process ID 1: The kernel launches the first user-space program, usually systemd, giving it a Process ID (PID) of 1.
            - Service orchestration: systemd reads configuration unit files to start background services like networking, logging, and user management in parallel.
            - Target state: It transitions the system into your default boot target, such as a multi-user text console or a graphical desktop environment.
        5. User Login
            - Display manager: The system launches a login prompt (CLI getty) or a graphical display manager (like GDM or LightDM).
            - Session start: You enter your credentials, and the system opens your user shell or desktop session.

	Kernel vs user space:
        - User space and kernel space are two distinct, hardware-enforced memory regions in an operating system that separate regular applications from the core operating system
        - User Spcae:
            - Definition: The memory area where normal user applications (like web browsers, text editors, and custom scripts) run.
            - Privileges: Runs with limited privileges (often called Ring 3 or user mode) and cannot access hardware directly.
            - Isolation: Each process gets its own private, isolated virtual memory space so one crashing app cannot affect another.
        - Kernel Space:
            - Definition: The protected memory area where the core operating system (the kernel), device drivers, and resource managers live.
            - Privileges: Runs with full, unrestricted access to all hardware and memory (often called Ring 0 or supervisor mode).
            - Stability: Controls critical tasks like CPU scheduling and memory allocation. A crash here can crash the entire system.

	Processes and threads:
        - A process is an independent program in execution with its own isolated memory space, while a thread is the smallest unit of execution within a process that shares that same memory space
        - Key Differences:
            - Memory: Processes have separate memory address spaces. Threads inside the same process share heap memory, code, and resources, but each has its own stack.
            - Weight: Processes are heavyweight and take more system resources. Threads are lightweight and require fewer resources.
            - Creation and Switching: Starting and stopping processes takes more time, and switching between them is expensive. Thread creation and context switching are fast.
            - Communication: Inter-process communication (IPC) is slow and complex. Inter-thread communication is fast because of shared memory.
            - Isolation and Safety: If a process crashes, it does not affect other processes. If a single thread corrupts shared memory, it can crash the entire process.

	Virtual memory:
        - Virtual memory is a memory management technique used by operating systems to extend physical RAM by temporarily using disk storage as an overflow space.
        - How Virtual Memory Works:
            - Address Translation: The CPU generates virtual addresses, which a hardware component called the Memory Management Unit (MMU) translates into physical RAM addresses.
            - Paging: Memory is split into fixed-size blocks called pages. Physical RAM is split into matching blocks called frames.
            - Swapping: When RAM fills up, the operating system moves inactive pages to a swap file (or page file) on the hard drive or SSD. When those pages are needed again, they are swapped back into RAM.

	Interrupt handling:
        - Interrupt handling is the process where a computer's central processing unit (CPU) temporarily stops its current task to respond to an urgent hardware or software event.
        - How Interrupt Handling Works:
            - Interrupt Request: A hardware device or software program sends an Interrupt Request Line (IRQ) signal to the CPU.
            - Context Saving: The CPU finishes the active instruction, saves the current program counter and register values onto the stack, and pauses the running process.
            - Service and Execution: The system runs the ISR code to manage the device or correct the error.
            - Restoration and Resume: The CPU restores the saved register states from the stack and resumes the original interrupted program.
        - Types of Interrupts:
            - Hardware Interrupts: Asynchronous signals sent by external peripheral devices like keyboards, mice, or network cards.
            - Software Interrupts (Exceptions): Synchronous events generated directly by the CPU during an instruction error, such as a division by zero or a page fault.
            - Maskable vs. Non-Maskable: Maskable interrupts can be temporarily ignored or delayed by the CPU, whereas non-maskable interrupts signal critical hardware errors that require immediate action.

	Synchronization: mutex, spinlock, semaphore:
        - Mutexes, spinlocks, and semaphores are kernel-level synchronization primitives used in concurrent programming to manage access to shared resources, prevent race conditions, and coordinate thread execution.
        - Quick Comparison:
            | **Feature**                  | **Mutex**                               | **Spinlock**                                                        | **Semaphore**                                                 |
            | ---------------------------- | --------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------- |
            | **Primary Purpose**          | Protect shared resources                | Protect shared resources for very short critical sections           | Resource counting / thread synchronization                    |
            | **Mechanism**                | Locking with ownership                  | Locking with ownership                                              | Signaling using an integer counter                            |
            | **Waiting Behavior**         | **Sleep/block** if unavailable          | **Busy-wait/spin** if unavailable                                   | **Sleep/block** if count is zero                              |
            | **Concurrent Access**        | **1 thread** at a time                  | **1 thread** at a time                                              | **N threads**, depending on semaphore count                   |
            | **Ownership**                | **Yes** — owner should unlock           | **Yes** — typically acquired/released by the same execution context | **No** — one context can signal/release what another acquired |
            | **CPU Usage While Waiting**  | Low — thread sleeps                     | High — CPU continuously spins                                       | Low — thread sleeps                                           |
            | **Context Switch**           | Possible when blocking                  | Usually no context switch while spinning                            | Possible when blocking                                        |
            | **Best Use Case**            | Protecting shared data/resources        | Very short kernel critical sections                                 | Resource pools, producer/consumer, event signaling            |
            | **Can Sleep While Holding?** | **Yes**                                 | **No**                                                              | Depends on how it is used                                     |
            | **Interrupt Context**        | **No**                                  | **Yes, with restrictions**                                          | **No** if operation may sleep/block                           |
            | **Typical Linux API**        | `pthread_mutex_lock()` / `mutex_lock()` | `spin_lock()`                                                       | `sem_wait()` / `down()`                                       |
            | **Example**                  | Protect shared linked list              | Protect short hardware/register operation                           | Allow up to N                                                 |

    1. Mutex (Mutual Exclusion)
        - A Mutex is a locking object designed to ensure that only one thread can access a critical section of code or a resource at any given moment.
    2. Spinlock
        - A Spinlock is a low-level synchronization lock where a thread continuously checks (or "spins" in a tight loop) until the lock becomes available.
    3. Semaphore
        - A Semaphore is a signaling mechanism that uses a non-negative integer variable to manage concurrent access to a pool of resources. It supports two primary atomic operations: wait() (traditionally called P) and signal() (traditionally called V).

	Kernel logging and debugging
        - Kernel logging and debugging encompass the vital mechanisms used to record system events, diagnose panics, and trace internal code execution within the Linux kernel.
        1. Kernel Logging Overview:
            - The foundation of Linux kernel logging is the printk() function, which acts as the kernel-space equivalent to printf().
            - The Kernel Ring Buffer:
                - All printk() outputs are directed to a fixed-size, cyclic memory structure known as the kernel ring buffer. Because it is a ring buffer, older data is overwritten once the buffer fills up.
                - Viewing Logs: You can retrieve these active messages using the user-space utility dmesg, or by viewing files like /var/log/kern.log and /var/log/messages.
                - Configuring Size: The buffer capacity is determined at compile time by CONFIG_LOG_BUF_SHIFT or at boot via the log_buf_len command-line argument.

	Device files
        - Device files in Unix-like operating systems like Linux are special interface files located in the /dev directory that allow software to communicate with hardware devices and drivers as if they were normal files.
        - Types of Device Files:
            1. Block Devices: Handle buffered data in chunks or blocks. They provide low-level access to storage hardware like hard drives and USBs (e.g., /dev/sda or /dev/nvme0n1).
            2. Character Devices: Handle unbuffered streams of data character by character. Examples include serial ports, keyboards, and terminals (e.g., /dev/tty).
            3. Pseudo-Devices: Do not represent physical hardware. They provide kernel functions, such as /dev/null (discards data) or /dev/random (generates random numbers).

	Sysfs and procfs:
        - In Linux, procfs and sysfs are RAM-based pseudo-filesystems that act as structural windows into the running Linux kernel. They do not store real files on a hard drive; instead, they generate virtual files on the fly to let user-space applications communicate directly with kernel-space parameters.
        - The primary difference lies in their intent: procfs focuses on process and system telemetry, while sysfs focuses on the device and driver hierarchy.
        - Direct Comparison:
            | **Feature**          | **`procfs` (`/proc`)**                                                                                       | **`sysfs` (`/sys`)**                                                                                                  |
            | -------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
            | **Primary Purpose**  | Exposes **process information and kernel/system runtime metrics**.                                           | Exposes and manages **devices, drivers, buses, and kernel objects**.                                                  |
            | **Core Philosophy**  | Historically more **information-oriented and less strictly structured**; many entries expose formatted text. | **Structured hierarchy** representing the Linux kernel's device model; attributes typically expose individual values. |
            | **Typical Use Case** | Monitoring **processes, memory, CPU, interrupts, kernel state**, etc.                                        | **Hardware discovery, device attributes, driver configuration, and device management**.                               |
            | **Main Users**       | System monitoring tools, debugging tools, administrators.                                                    | Device-management tools, udev, applications, administrators, drivers.                                                 |
            | **Examples**         | `/proc/cpuinfo`, `/proc/meminfo`, `/proc/interrupts`, `/proc/<PID>/`                                         | `/sys/class/net/`, `/sys/class/leds/`, `/sys/class/block/`, `/sys/devices/`                                           |
            | **Kernel Concept**   | Process and system information exposed through **procfs**.                                                   | Kernel objects represented using **kobjects, ksets, buses, devices, and attributes**.                                 |
            | **Hardware Focus**   | Secondary; may expose hardware-related runtime information.                                                  | **Primary focus** for the Linux device model and hardware/driver relationships.                                       |
            | **Configuration**    | Some kernel parameters can be change                                                                         |                                                                                                                       |

        1. The Process Filesystem: procfs (/proc):
            - Historically, procfs was designed to expose information about running processes (hence the name proc). Over time, developers started putting everything into /proc, creating a disorganized mix of system information.
            - /proc/[PID]/: Every running process gets its own directory named after its Process ID. It contains runtime parameters like cmdline (how it was executed), fd/ (open file descriptors), and status.
            - Global System Telemetry: Files like /proc/meminfo (RAM status) and /proc/cpuinfo (processor specs) are parsed by tools like top, free, and vmstat to display live statistics.
            - /proc/sys/: A specialized subdirectory utilized by the sysctl command to tune global kernel behaviors dynamically without requiring a reboot.
        2. The System Filesystem: sysfs (/sys):
            - Introduced in the Linux 2.6 kernel, sysfs was specifically created to offload non-process hardware trees out of /proc and into a clean, uniform hierarchy. It maps out exactly how components connect to the motherboard, buses, and driver subsystems.
            - Kernel Object Mapping: Every directory corresponds to an internal kernel tracking element (kobject).
            - Structured Control: Because it enforces a strict "one value per file" policy, changing a setting is as simple as echoing a variable to a file (e.g., modifying power management or a CPU frequency scaling governor).
            - Device Management: Subsystems like udev dynamically monitor /sys to detect newly attached hardware (like a USB drive or SD card) and automatically map it into /dev.

        - The Linux kernel acts as the core of the operating system, managing the communication between your system hardware and software applications. To keep the system lightweight and flexible, Linux balances what features are permanently built into the core kernel against what can be loaded on demand using kernel configuration and kernel modules.

        -  Kernel Configuration:
            - Kernel configuration determines exactly what features, drivers, and protocols are included in the compiled kernel image.
            - The .config File: The entire state of a kernel's configuration is saved in a hidden file named .config inside the kernel source directory. This file uses symbols prefixed with CONFIG_ to define system properties.
            - Tristate Options: Most option symbols use a "tristate" logic during configuration:
                        Linux Kernel Configuration
                                 │
                ┌────────────────┼────────────────┐
                │                │                │
                Built-in         Module          Disabled
                (y)             (m)               (n)
                │                │                │
            Inside vmlinux     .ko file       Not included
            / Image            Load later
                    - Built-in (y) → compiled directly into the kernel
                    - Module (m) → compiled as a loadable .ko module
                    - Disabled (n) → not compiled
            - Configuration Tools: Instead of editing .config by hand, administrators use menu-driven compilation interfaces:
                - make menuconfig: A terminal-based ncurses interface (most common).
                - make oldconfig: Updates an existing .config file to match a newer kernel source.

            - Kernel Modules:
                - Kernel modules (also called Loadable Kernel Modules or LKMs) are independent segments of code that can be dynamically inserted or removed from a running kernel without needing to reboot the system.
                - Purpose: They are primarily used for device drivers (e.g., graphics cards, Wi-Fi adapters), filesystem drivers (e.g., NTFS, ext4), and system security extensions.
                - Storage Location: Compiled modules are stored as object files ending in .ko (or compressed .ko.xz) and reside in /lib/modules/$(uname -r)/. Because modules are tied to exact kernel builds, every kernel version has its own distinct directory here.
                - Essential Kernel Module Management Commands:
                    | Command           | Purpose                                                                                                                 | Example                          |
                    | ----------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
                    | **`lsmod`**       | Lists currently loaded kernel modules, including their size and usage/dependency information.                           | `lsmod`                          |
                    | **`modinfo`**     | Displays detailed information about a kernel module such as description, author, license, parameters, and dependencies. | `modinfo nvme`                   |
                    | **`modprobe`**    | **Preferred tool** for loading a module. Automatically handles required module dependencies.                            | `sudo modprobe bluetooth`        |
                    | **`modprobe -r`** | Removes a module and, when possible, its unused dependencies.                                                           | `sudo modprobe -r bluetooth`     |
                    | **`insmod`**      | Directly inserts a specific `.ko` module file. It does **not automatically resolve dependencies**.                      | `sudo insmod /path/to/driver.ko` |
                    | **`rmmod`**       | Directly removes a loaded module. It does not perform dependency management like `modprobe -r`.                         | `sudo rmmod driver`              |
                    | **`depmod`**      | Generates/rebuilds the module dependency and metadata files under `/lib/modules/<kernel-version>/`.                     | `sudo depmod -a`                 |

	Cross-compilation:
        - Cross-compilation is the process of compiling source code on one computer system (the build/host machine) to generate executable binaries for a completely different computer system (the target machine). This differs from native compilation, where code is compiled and executed on the exact same architecture and operating system.
        - Core Terminology:
            - Cross-compilation relies on three distinct environment definitions, often specified via a target triple (e.g., x86_64-unknown-linux-gnu or aarch64-none-elf):
                - Build Machine: The platform where the compilation takes place (typically a powerful workstation or CI/CD server).
                - Host Machine: The platform where the compiler itself runs (usually the same as the build machine).
                - Target Machine: The platform where the final compiled executable binary will run.

                | **Feature**             | **Native Compilation**                                          | **Cross-Compilation**                                                     |
                | ----------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------- |
                | **Build Platform**      | Compiler runs on the same type of system as the target.         | Compiler runs on a different system/architecture from the target.         |
                | **Execution Platform**  | Program normally runs on the same system where it was compiled. | Program runs on a different target system or architecture.                |
                | **Compiler**            | Native compiler, e.g. `gcc`                                     | Cross compiler, e.g. `aarch64-linux-gnu-gcc`                              |
                | **Common Use Case**     | Desktop applications, server software, local development        | Embedded Linux, microcontrollers, IoT, mobile/ARM systems                 |
                | **Output**              | Binary for the local architecture, e.g. x86_64 ELF              | Binary for the target architecture, e.g. ARM64 ELF                        |
                | **Headers & Libraries** | Uses local system headers and libraries                         | Uses target-specific headers and libraries, usually through a **sysroot** |

                | **Execution**           | Can usually execute immediately on the build machine            | Usually copied/transferred to the target before execution                 |

	What is a BSP?

	Boot ROM → Bootloader → Kernel → Root filesystem:
        - The sequence Boot ROM → Bootloader → Kernel → Root filesystem outlines the standard initialization flow for embedded and desktop operating systems like Linux.
        - This flow will be chnage in CPU and SoC. Every CPU and SoC has diffrent diffrent flow.
        1. Boot ROM:
            - What it is: Hardwired, read-only code built directly into the processor chip (SoC).
            - What it does: It executes first when power turns on, initializes minimal core hardware (like internal clocks and basic memory), and searches for an external storage device or flash memory to find the next stage.
        2. Bootloader:
            - What it is: A small software program (such as U-Boot on embedded devices or GRUB on PCs).
            - What it does: It sets up external RAM, configures essential peripherals, loads the operating system kernel image into memory, and passes startup parameters to it.
        3. Kernel:
            - What it is: The core engine and central manager of the operating system.
            - What it does: It decompresses itself, detects and activates hardware device drivers (like storage, display, and USB), configures memory management, and mounts the root filesystem.
        4. Root Filesystem (RootFS):
            - What it is: The top-level directory structure mounted at / that holds the user-space environment.
            - What it does: It provides essential system binaries, configurations, libraries, and tools (/bin, /etc, /lib), and launches the initial process (init or systemd) to bring the system fully online.
    
	Toolchain and cross-compilation:
        - A cross-compilation toolchain is a set of programming tools running on one system (the host) that builds executable software to run on a different system (the target).
        - Key Machine Roles:
            - To understand cross-compilation, you must look at three distinct machine environments:
            - Build: The machine where the toolchain itself is compiled.
            - Host: The machine where the toolchain runs (your development PC).
            - Target: The machine where the final compiled program runs (like an embedded device or different OS).
        - Core Anatomy of a Toolchain:
            - Compiler (e.g., GCC, Clang): Translates human-readable source code into target assembly code.
            - Binutils (Assembler and Linker): Turns assembly code into object files and links them into a final binary.
            - C Library (e.g., glibc, musl): Provides standard system functions and interfaces.
            - Sysroot: A directory tree holding the target system's specific headers and libraries.

	Board-specific code:
        - Board-specific code refers to software or configuration files written to support a unique physical hardware design (a printed circuit board or PCB) rather than a generic processor architecture.
        - In embedded systems and operating system development, it isolates the hardware quirks, physical layouts, and pin connections of a specific board so that the primary operating system kernel or application code can remain hardware-agnostic.
        -  Components of Board-Specific Code:
            - Depending on the ecosystem, board-specific code usually covers:
            - Pin Mapping & Multiplexing: Directing internal microcontroller/SoC pins to external physical headers (e.g., mapping a specific pin to function as a UART TX or a status LED).
            - Peripheral Initialization: Configuring on-board clock frequencies, memory partitions (RAM/Flash sizes), and initializing buses like I2C, SPI, and GPIO controllers.

	Device Tree:
        - A Device Tree is a data structure that describes the hardware components of a board to the Linux kernel. It allows the kernel to discover and configure hardware without hardcoding every board's details into the kernel source code.
        - Why Do We Use It?
            - Before Device Trees became the standard for architectures like ARM, MIPS, and PowerPC, hardware details were hardcoded directly into the kernel source files. This led to massive code duplication and required a separate kernel build for every single variation of a board.
            - The Device Tree solves this via three core use cases in Linux:
                - Platform Identification: The kernel reads the tree to find out exactly what machine it is running on.
                - Runtime Configuration: Pass essential parameters—like the kernel boot arguments (bootargs), standard console paths, or memory locations—from the bootloader directly to the operating system.
                - Dynamic Device Population: The kernel parses the tree to discover non-discoverable hardware (like I2C, SPI, or memory-mapped peripherals) and matches them to their corresponding device drivers.

4. Bootloader
---------------------------------------------------------------
	Boot ROM concepts:
        - A Boot ROM (Boot Read-Only Memory) is a small, immutable block of code permanently burned or embedded directly into the silicon of a System-on-Chip (SoC) or processor. It acts as the very first set of instructions executed when the device powers on or resets.
        - Core Concepts:
            - Root of Trust: Because it is burned into the hardware at the factory (usually as a Mask ROM), it cannot be modified or updated. This immobility makes it the fundamental hardware root of trust for the entire device.
            - Fixed Reset Vector: Upon power-on or hardware reset, the CPU begins fetching and executing instructions from a hardwired, immutable memory address known as the reset vector, which points directly to the Boot ROM.
            - Minimal Hardware Initialization: The Boot ROM does only what is strictly necessary to get the system moving—configuring basic CPU states, setting up internal clocks, Phase-Locked Loops (PLLs), and initializing internal SRAM or tightly coupled memory (TCM).
            - Boot Media Selection: It reads hardware configuration pins (such as strap resistors, GPIOs, or BOOT_SELECT_CODE fuses) to determine where the next-stage bootloader or firmware resides (e.g., eMMC, UFS, SPI flash, SD card, or USB/UART interfaces).
            - Cryptographic Authentication & Secure Boot: To prevent malicious code execution, the Boot ROM reads public keys or hash digests from eFuses, validates cryptographic signatures (like RSA or SHA-512) on the next-stage bootloader (such as a Primary Bootloader or SPL), and establishes the chain of trust.
            - Fallback and Recovery Modes: Many implementations support redundant boot chains or specialized emergency recovery states (such as USB DFU/Interactive mode) if primary boot media verification fails.
            - Vulnerability & Exploits: Because Mask ROM is unpatchable after silicon fabrication, hardware bugs or logic flaws inside a Boot ROM (such as Apple’s SecureROM or NVIDIA Tegra flaws) cannot be fixed via software updates, often leading to permanent hardware-level jailbreaks or custom exploits.
            
	U-Boot architecture:
        - Das U-Boot (Universal Boot Loader) relies on a modular, multi-stage architecture designed to manage the strict memory constraints of embedded systems. It acts as a hardware abstraction bridge between power-on and operating system execution.
        - The architecture is structured into clear computational stages, a standardized driver abstraction layers framework, and specialized configuration and runtime subsystems.
        
        1. Multi-Stage Execution Model:
            - Embedded systems often start up with access only to a tiny internal static RAM (SRAM) before the main dynamic memory (DRAM) is initialized. To handle this, Das U-Boot splits its execution into distinct sequential images:
            - Secondary Program Loader (SPL): A highly optimized, minimal first-stage binary. It fits entirely within internal SRAM. Its primary responsibilities are low-level clock configuration, pin multiplexing, and initializing the DRAM controller. Once RAM is operational, the SPL loads the next phase into full memory and transfers execution.
            - Tertiary Program Loader (TPL): An optional ultra-minimal layer used in specific systems (such as Rockchip SoCs) when the internal SRAM is too small to fit even a full SPL framework. It initializes the bare minimum required to load the SPL.
            - U-Boot Proper: The full-featured second-stage environment. It includes the command-line interface (CLI), advanced file systems, network stacks, and execution shells (hush). It handles the discovery and loading of the OS kernel and Device Tree Blobs (DTB) into memory.
                    [ SoC Mask ROM ] ➔ [ TPL (Optional) ] ➔ [ SPL (Runs in SRAM) ] ➔ [ U-Boot Proper (Runs in DRAM) ] ➔ [ Linux Kernel ]
        
        2. Core Architectural Subsystems:
            - Driver Model (DM) : 
                - Modern implementations rely on a Linux-like Driver Model to prevent hardware dependency sprawl. It organizes peripherals hierarchically via structural components:
                - Lists / Uclasses: An abstract group of devices sharing the same operational interface (e.g., UCLASS_SERIAL, UCLASS_I2C, UCLASS_BLK).
                - Drivers: The hardware-specific implementations bound to a specific node.
                - Devices: Concrete logical instances of a driver bound to actual hardware.
            - Device Tree Integration:
                - Hardware layout is completely decoupled from the source code. Das U-Boot natively parses a Flattened Device Tree (FDT)—the same format utilized by the Linux kernel—to identify what hardware is present. For early bootstrap code like the SPL, special properties (such as bootph-ram or bootph-all) indicate to the builder which essential nodes must be compiled directly into the constrained SPL binary.
            - Environment Variables Subsystem:
                - Runtime customization is managed via a dedicated, persistent environment block. Variables dictate boot scripts, network addresses, and manual terminal flags. It supports volatile operation or hard persistence across non-volatile storage blocks (eMMC, SPI Flash, NVMe) using standard shell interaction hooks (printenv, setenv, saveenv).
            - Standard Boot (bootstd):
                - Recent architectural updates replace unpredictable, fragile shell scripting macros with structural device interfaces via U-Boot Standard Boot Documentation:
                - bootdev: Represents a physical boot device instance (e.g., MMC, PCIe, USB, Ethernet).
                - bootmeth: Implements the software discovery strategy needed to locate files (e.g., searching for a EFI system partition or standard distro-boot file).
                - bootflow: Houses the generated parameters dictating exactly how a discovered OS image should execute.

	U-Boot environment:
        - The U-Boot environment is a dedicated block of non-volatile, persistent storage used by the Das U-Boot bootloader to store runtime configuration parameters as name=value pairs.
        - Protected by a CRC32 checksum to prevent data corruption, these environment variables dictate critical behaviors—such as where to load the operating system from, how much time to wait before auto-booting, and what argument flags to pass to the Linux kernel.
        
        1. ⚙️ How It Works (RAM vs. Storage):
            - Boot Initialization: When the device powers on, U-Boot copies the persistent environment variables from non-volatile storage (such as eMMC, NAND flash, SPI flash, or SD cards) into a RAM-resident hash table for high-performance lookups.
            - Runtime Modifications: Commands like setenv or env set only modify the RAM instance of the environment variables.
            - Persistence: Changes are volatile and will disappear upon a reboot unless explicitly committed to physical storage using the saveenv or env save command.

        2. 🛠️ Common Commands in U-Boot Shell
            - You can manage environment variables directly from the U-Boot serial console using either legacy shorthand commands or modern env subcommands:
                | Modern Command         | Legacy Alias  | Description                                                               |
                | -----------------------| --------------| ------------------------------------------------------------------------- |
                | `env print`            | `printenv`    | Displays all current environment variables and their values.              |
                | `env set [name] [value]|`setenv`       | Creates or updates a variable. Omitting the value deletes it.             |
                | `env save`             | `saveenv`     | Saves the current environment variables to persistent storage.            |
                | `env default -a -f`    | None          | Resets all variables to the compiled-in default values.                   |
                | `run [variable]`       | `run`         | Executes the command or script stored in the specified environment variable. |
        
        3. 🔑 Critical Environment Variables
            - U-Boot variables act as a powerful scripting language supporting loops, conditional statements (if/for), and sequential execution (separated by semicolons). Some of the most crucial variables include:
            - bootcmd: The most critical variable. It contains the default command sequence U-Boot automatically runs when the bootdelay timer expires.
            - bootargs: The string passed directly to the Linux kernel as its command-line parameters (e.g., specifying the root filesystem location, init system, or console UART baudrate).
            - bootdelay: The number of seconds U-Boot waits for user input on the serial console before executing bootcmd automatically.
            - ethaddr: The hardcoded MAC address for the device's network interface. For security and networking stability, this variable is write-once and locked after its first assignment during factory manufacturing.
            - ipaddr / serverip: Static network configuration variables used to pull kernel images remotely over TFTP.

    SPL/TPL:
        - SPL (Secondary Program Loader) and TPL (Tertiary Program Loader) are early-stage bootloader components used in embedded systems (such as Das U-Boot) and can also refer to TPLSPL (TPL Services Private Limited), a subsidiary of Tata Projects Limited handling industrial operations and maintenance.
        
        1. U-Boot Bootloader Stages (SPL / TPL):
            - In embedded board boot sequences, the initial internal SRAM or ROM is too small to fit the full U-Boot image. The boot process is split into incremental lightweight stages:
            - TPL (Tertiary Program Loader):
                - Role: The very first and smallest code stage used on select hardware (such as certain PowerPC or complex SoC boards) where initial memory is too tight even for SPL.
                - Function: Performs ultra-early hardware initialization and loads the SPL binary.
            - SPL (Secondary Program Loader):
                - Role: The second-stage loader (often called a first-stage loader relative to the OS).
                - Function: Initializes main external RAM (SDRAM/DDR) and loads the main U-Boot proper image (or alternative payloads like OpenSBI or ARM Trusted Firmware).
            - VPL (Verifying Program Loader):
                - Role: An optional verification step between TPL and SPL used for A/B verified boot flows.

	DDR initialization:
        - DDR initialization is the multi-step boot and configuration sequence where a system controller and physical layer (PHY) power up, calibrate, and train external DRAM (DDR3, DDR4, or DDR5) so reliable high-speed data transfers can occur.
        - Key Phases of DDR Initialization:
            1. Power-Up & Reset Sequence:  
                - Apply board power rails and stabilize clocks and reset signals (e.g., holding RESET_n low per JEDEC specifications, typically ≥ 200 μs).
                - Release internal resets and initialize the DDR controller and PHY timing modules.
            2. Controller & PHY Register Configuration:
                - Program memory controller timing parameters (such as tRCD, tRP, tRAS, CAS latency) and address/data widths.
                - Configure ZQ impedance calibration using an external 240-ohm precision resistor to tune drive strength and on-die termination (ODT).
            3. JEDEC Mode Register Programming:
                - Send standard power-up commands (NOP, Precharge All, Refresh).
                - Write to internal Mode Registers (MR0 through MR6) to set burst lengths, latencies, and operational modes.
            4. PHY Training & Calibration:
                - DLL Lock: Lock the delay-locked loop circuits for clock-data synchronization.
                - Write Leveling: Align the clock (CK) and strobe (DQS) signals for write operations.
                - Read Gate / Read Training: Synchronize DQS and DQ signal windows during reads, often using multi-purpose register (MPR) patterns.
                - \(V_{\text{ref}}\text{DQ}\) Calibration: Center-align internal reference voltages for pseudo-open drain (POD) signaling.

	Clock initialization:
        - Clock initialization is the hardware and software sequence that sets up a microcontroller, system-on-chip (SoC), or digital logic block's internal clock tree, frequency sources, and phase-locked loops (PLLs).
        - Core Steps in Clock Initialization:
            1. Enable Oscillators: Turn on internal or external high-frequency and low-frequency crystal oscillators (such as HFXO/HFRCO or LFXO/LFRCO).
            2. Wait for Stabilization: Poll status registers (like MCLKSTATUS or oscillator ready flags) to ensure clock signals are stable before switching.
            3. Configure PLL and Multipliers: Set up Phase-Locked Loops to scale a lower-frequency reference clock up to the target core/system frequency (e.g., 180 MHz).
            4. Set Prescalers and Dividers: Adjust bus and peripheral dividers (AHB, APB, timers) so that individual peripherals do not exceed their maximum allowed frequency.
            5. Switch Main Clock Source: Transition the system core clock over to the newly configured high-speed source or PLL.
            6. Update System Variables: Call core update functions (such as SystemCoreClockUpdate() in CMSIS or equivalent HAL routines) so software-dependent delays and timers (like SysTick) scale accurately.

	Pinmux initialization:
        - Pinmux (pin multiplexing) initialization configures a System-on-Chip's (SoC) physical I/O pins to route specific internal peripheral signals (such as UART, I2C, SPI, or GPIO) to the external package pins, along with electrical pad characteristics.
        - Core Components of Pinmux Initialization:
            1. Function / Mux Mode Selection: Assigns a specific peripheral function (e.g., UART0_TXD, SPI1_CS) to a physical pin using a multiplexer selection register or function ID.
            2. Pad Control / Electrical Configuration: Configures internal resistors and buffer properties:
                - Pull-up / Pull-down: Enables or disables internal weak pull-up or pull-down resistors.
                - Receiver / Input Enable (RX_EN): Turns on the input buffer. Many peripherals (like I2C clocks, SPI chip selects, and MMC/SD lines) require input buffers enabled even when operating as outputs.
                - Drive Strength (DSE): Adjusts output current drive capability (e.g., 1mA, 4mA).
            3. Termination / End Marker: In bare-metal or SDK drivers, arrays of pinmux configurations are typically terminated with a sentinel value (e.g., PINMUX_END) so the initialization loop knows where configuration stops.

	PMIC initialization:
        - PMIC (Power Management Integrated Circuit) initialization is the process of powering up, configuring communication interfaces (such as I2C, SPI, or SPMI), setting regulator/LDO output voltages, and releasing the system or CPU reset line.
        - Key Stages of PMIC Initialization:
            1. Hardware Power-Up & Sequencing:
            2. Interface Setup & Driver Handle:
            3. Register Configuration:
            4. Reset Release:

	Storage initialization:
        - Storage initialization is the process of preparing a storage device, drive, or memory space so that an operating system or program can recognize, manage, and use it.
        - What Happens During Storage Initialization:
            1. Operating Systems (Windows/Mac/Linux): Prepares a brand-new or replacement hard drive (HDD) or solid-state drive (SSD) by writing a partition style—such as GPT (GUID Partition Table) or MBR (Master Boot Record)—so the OS can create volumes and file systems (like NTFS).
            2. Programming & Software: Assigns initial or default values to variables, arrays, or memory allocations (such as zero-initializing static variables or setting up heap/stack memory) before a program executes.
            3. Cloud & Enterprise Storage: Allocates storage blocks, sets up metadata, or streams base data from sources like Amazon S3 to make cloud databases or RAID arrays operational.

	Ethernet/USB boot:
        - Ethernet or USB booting—often used for PXE (Preboot Execution Environment) network installation or booting from an external USB/Ethernet adapter—requires specific hardware, BIOS settings, and driver compatibility.
        - Core Requirements for USB-to-Ethernet PXE Boot:
            - UEFI/BIOS Support: Your computer's firmware must natively support PXE booting through the specific USB Ethernet adapter or USB-C/Thunderbolt controller. Not all generic adapters work in UEFI mode.
            - BIOS Settings:
                - Enable the Network Stack / UEFI PXE Boot / LAN PXE Option ROM.
                - Enable Thunderbolt Boot support if using a USB-C/Thunderbolt adapter (e.g., on Dell or similar enterprise hardware).
                - Adjust Fastboot or Legacy Option ROM settings according to your system guidelines (such as setting Fastboot to "Thorough").
            - MAC Pass-Through / Duplicate MACs: USB adapters have their own MAC addresses, which can conflict on deployment servers like SCCM. Enabling MAC Pass-Through in the BIOS helps pass the host device's actual MAC address.
            - Server Setup: A configured PXE/TFTP/WDS (Windows Deployment Services) or iPXE server must be active on the local network to serve the boot images.

	Boot arguments:
        - Boot arguments (or boot flags) are configuration parameters passed directly to an operating system's kernel during startup to control hardware behavior, enable debugging, or troubleshoot issues.

	Device Tree handoff:
        - A Device Tree handoff refers to the structured process where early-stage boot software passes a compiled hardware description binary (Device Tree Blob or DTB) down the bootloader chain to the operating system kernel. In embedded systems and architectures lacking automatic hardware discovery (like ARM, RISC-V, and specific SoC architectures), this handoff is crucial because it informs the incoming software layer exactly what hardware components exist, where they are mapped in memory, and how they are configured.
        
        🔄 The Standard Handoff Chain:
            - Rather than compiling distinct hardware tables into every single stage of boot firmware, a single cohesive hardware description is passed and mutated down the line:
                    [ First-Stage Bootloader ] (e.g., TF-A / SPL)
                            │
                            ▼  Passes raw memory layout / basic configurations
                    [ Second-Stage Bootloader ] (e.g., U-Boot / EDK2)
                            │
                            ▼  Applies Overlays (.dtbo) & fixes up system variables
                    [ Operating System Kernel ] (e.g., Linux Engine)

            1. First-Stage Bootloader (FSBL/SPL): Initializes vital low-level components like DDR memory and system clocks. It reads hardware strap pins or EEPROMs to determine the physical board variation.
            2. Second-Stage Bootloader (e.g., U-Boot): Receives the initial DTB pointer from the FSBL. U-Boot uses its integrated fdt (Flattened Device Tree) engine to modify the tree in RAM dynamically. This is known as a Device Tree Fixup.
                - Examples: Modifying the available RAM size, injection of MAC addresses, or choosing which dynamic Device Tree Overlays (.dtbo) to apply based on attached expansion boards.
            3. The Final Kernel Handoff: When calling the kernel boot instruction (e.g., bootm or bootz), U-Boot places the memory pointer of the finalized, combined DTB into a specific CPU register (r2 on ARM32, x0 on ARM64). The Linux kernel parses this address upon initialization to bind its platform drivers to the correct physical devices.
        
        🛠️ Evolving Standards in Device Tree Handoffs:
            - Modern system design guidelines have shifted how handoffs occur to accommodate security and multi-tenant architectures:
                1. System Device Tree (SDT) & AMD/Xilinx SHEL Flow
                2. Firmware-Owned Trees (ARM SystemReady / EBBR)
        
        ⚠️ Common Handoff Failure Points:
            - Memory Collisions: If the bootloader loads the DTB into a RAM area that the Linux kernel immediately overwrites during early decompression routines, the handoff pointer corrupts.
            - Architecture-Register Mismatches: If the register holding the DTB physical address gets wiped or modified right before jumping to the kernel entry point, the kernel will fail to boot because it cannot find the root hardware layout.
            - Overlay Incompatibilities: Applying a .dtbo overlay compiled against a different base version of the firmware tree can break logical phandle pointers, resulting in failed runtime driver parsing.

	FIT images:
        - A FIT (Flattened Image Tree) image is a single container format used in embedded Linux to bundle multiple boot components—such as the Linux kernel, Device Tree Blobs (DTBs), Initramfs/Ramdisks, and even FPGA bitstreams—into a single binary file.
        - It replaces the old legacy uImage format and uses the standard Device Tree syntax to define how these components are packaged and loaded into memory.
        
        - Key Advantages of FIT Images:
            - 📦 Single File Management: Instead of maintaining separate files for kernel, DTB, and rootfs on your flash storage, you handle just one file (typically named fitImage or with a .itb extension).
            - 🔒 Verified Boot & Security: Individual elements can be hashed (SHA-1/SHA-256) and cryptographically signed (RSA/ECDSA). U-Boot will verify the signature before executing the kernel, creating a secure chain of trust.
            - 🎛️ Multiple Configurations: A single FIT image can hold multiple DTBs or kernels. U-Boot can dynamically pick the correct configuration matching the hardware variant at runtime.

        - How FIT Images Work:
            - .its (Image Tree Source): A text file written in Device Tree syntax describing what binaries to include and where they belong in memory.
            - .itb (Image Tree Blob): The compiled binary output that gets flashed to the device.
                    [kernel, dtb, rootfs] + [config.its] ===(mkimage tool)===> image.itb ===(flashed to device)===> Loaded by U-Boot
            
        - Implementation Example:
            1. Define the Image Tree Source (image.its)
            2. Compile the FIT Image
            3. Booting in U-Boot
            4. Inspecting FIT Images in U-Boot

	Secure boot basics:
        - Secure Boot is a security standard that ensures your computer only executes manufacturer-approved, trusted software during the startup process. It acts as a digital bouncer, verifying the authenticity and integrity of every piece of code before handing over control.
        - How Secure Boot Works:
            - Root of Trust (RoT): The process begins with an immutable (unchangeable) piece of code hardcoded into the hardware or boot ROM. This forms the foundation of trust.
            - Chain of Trust: Each stage of the boot sequence (firmware, bootloader, and operating system kernel) cryptographically verifies the digital signature of the next stage before loading it into memory.
            - Signature Databases: The UEFI firmware uses specialized NV-RAM storage containing databases to validate code:
                PK (Platform Key): Establishes trust between the hardware owner and the firmware.
                KEK (Key Enrollment Key): Connects the operating system provider to the firmware signature databases.
                db (Authorized Database): Holds trusted public keys and certificates.
                dbx (Revoked Database): Holds blacklisted or compromised certificates, taking strict precedence over the authorized database.
            - Failure Action: If any signature is invalid, missing, or listed in the revoked database (dbx), Secure Boot halts the boot process or forces the system into recovery mode.

	

5. Device Tree
---------------------------------------------------------------
	DTS / DTSI structure:
        - A DTS (Device Tree Source) and DTSI (Device Tree Source Include) structure organizes hardware descriptions in a hierarchical tree format so the Linux kernel or firmware can recognize non-discoverable board components without hardcoding them.
        - Core File Types:
            1. DTSI (.dtsi - Device Tree Source Include): Acts like a C-language header file (.h). It holds reusable, generic hardware definitions for components like the SoC (System-on-Chip), CPU cores, or System-on-Module (SoM). Peripherals inside an SoC DTSI are typically marked status = "disabled" by default because not every board uses every feature.
            2. DTS (.dts - Device Tree Source): The main, human-readable entry file representing a specific physical board or model (one .dts file per board). It includes the relevant .dtsi files and applies board-specific overrides, pinmux settings, and enables active hardware.
            3. DTB (.dtb - Device Tree Blob): The compiled binary version of the DTS/DTSI files, generated via the DTC (Device Tree Compiler), which is loaded by the bootloader or kernel.
        - Typical 3-Tier Hierarchy:
            1. SoC Level (soc.dtsi): Defines internal memory-mapped peripherals, UARTs, I2C controllers, timers, and CPU bus architecture built into the chip.
            2. SoM / Module Level (som.dtsi - optional, common in modular designs like Toradex): Includes the SoC .dtsi and adds components fixed to the module itself (such as on-module RAM size, power management ICs, or wireless chips).
            3. Board / Carrier Level (board.dts): 

	Nodes and properties:
        1. Device Tree Nodes:
            - Nodes represent actual hardware devices, sub-systems, or buses.
            - The Root Node: Every device tree starts with a single root node, represented by a forward slash (/).
            - Hierarchy: Nodes can contain other sub-nodes (child nodes) to mirror the physical layout of the chip or board. For example, a I2C controller node will host child nodes representing individual I2C sensors.
            - Naming Convention: Nodes use the syntax node-name@unit-address. The unit-address typically points to the primary memory address or bus address of the device.
                    / {  /* Root Node */
                        soc {  /* Child node representing System on Chip */
                            serial@101f1000 {  /* Sub-child node with unit-address */
                                /* Properties go here */
                            };
                        };
                    };

        2. Device Tree Properties:
            - Properties are key-value pairs stored inside nodes that describe specific attributes of that hardware.

        3. Common Standard Properties:
            - The Linux kernel depends on several standard properties to bind drivers and configure system resources:
                +-------------+-------------------+--------------------------------------------------------------------------------------------------+
                | Property    | Value Type        | Description                                                                                      |
                +-------------+-------------------+--------------------------------------------------------------------------------------------------+
                | compatible  | String List       | Identifies the device so the Linux kernel can bind the appropriate driver.                       |
                | reg         | Cells (< >)       | Defines the register address range or bus address and the size allocated to the device.          |
                | status      | String            | Specifies whether the device is enabled or disabled. Common values are "okay" and "disabled".    |
                | interrupts  | Cells (< >)       | Specifies the interrupt lines used by the hardware device.                                       |
                | clocks      | Cells (< >)       | References the clock sources required by the peripheral.                                         |
                | phandle     | Cell (32-bit int) | A unique numerical identifier used to reference a device tree node from other nodes.             |
                +-------------+-------------------+--------------------------------------------------------------------------------------------------+

        4. Special System Nodes:
            - Outside of hardware peripherals, there are standard architectural nodes used to configure the kernel environment:
            - cpus: Lists the available CPU cores and their configurations.
            - memory: Tells the kernel the physical address range and size of the system's RAM.
            - chosen: Used by the bootloader (like U-Boot) to pass dynamic information to the kernel, such as the command-line arguments (bootargs).
            
	compatible:
        - The compatible property tells Linux what type of hardware a Device Tree node describes.
        - Linux uses it to match a Device Tree node with a driver that supports that hardware.

	reg:
        - The reg property describes the address and size of a device's register region or other addressable resources.
        - The interpretation depends on the parent bus's #address-cells and #size-cells properties.

	interrupts:
        - The interrupts property specifies which interrupt a device uses.
        - The meaning of the cells in interrupts depends on the interrupt controller's binding.

	clocks:
        - Hardware peripherals often require clocks to operate.
        - The clocks property connects a device to one or more clock providers.

	resets:
        - Many peripherals must be taken out of reset before they can operate.
        - The resets property specifies the reset controller and reset line associated with a device.

	gpios:
        - GPIOs are used for simple digital input and output signals.
        - The GPIO controller label and GPIO identifier are illustrative.

	pinctrl:
        - Modern SoCs often share physical pins between several functions.
        - The pin controller configures which function is connected to a pin and may also configure pull-up, pull-down, drive strength, and other electrical properties.

	dma:
        - DMA allows hardware peripherals to transfer data to or from memory with reduced CPU involvement.

	Device Tree overlays:
        - A Device Tree overlay applies changes to a base Device Tree.
        - It can enable a peripheral, add a device on an available bus, or modify an existing node without maintaining a completely separate copy of the base DTS.
        - Overlay support depends on the bootloader, kernel configuration, and platform integration.

	Device Tree debugging:
        - Device Tree debugging helps determine whether the intended hardware configuration actually reached the running kernel and whether the kernel successfully created the corresponding device.

	Mapping Device Tree nodes to drivers:
        - This is one of the most important concepts when developing or debugging an embedded Linux BSP.
        - A Device Tree node does not directly call a driver function. Instead, the kernel creates devices and matches them against registered drivers.

6. Linux Device Drivers
---------------------------------------------------------------
	Learn these in roughly this order:
	Kernel module development:
        - Linux Loadable Kernel Modules (LKMs) are pieces of object code that dynamically expand the kernel's capabilities at runtime without requiring a full system reboot. They run directly in Ring 0 (kernel space), giving them full hardware privileges. Because they lack the memory sandboxing found in user space, a single unhandled pointer or structural error can trigger a kernel panic rather than a simple segmentation fault.
        - Development steps:
            1. Set Up the Development Environment
            2. Write the C Source Code
            3. Define the Kbuild Makefile
            4. Build the Module
            5. Load, Verify, and Unload

	Character drivers:
        - A character device driver is a Linux or Unix kernel module that manages hardware by transmitting data as a sequential stream of bytes (one character at a time) rather than in large blocks.
        
        - Key Characteristics:
            1. Sequential Access: Data is read or written in a continuous stream without random-access seeking (unlike block devices like hard drives).
            2. Examples: Keyboards, mice, serial ports, sound cards, and custom hardware nodes.
            3. Filesystem Nodes: They appear as special files in the /dev directory (starting with c in ls -l outputs).
        
        - Core Components in Linux:
            1. Major number: Identifies which driver handles the device.
            2. Minor number: Distinguishes a specific physical device or instance managed by that driver.
            3. struct file_operations: A table of function pointers connecting system calls from user-space down to the driver code. Common operations include:
                - open() – Initializes or allocates resources when the device file is opened.
                - read() – Copies data from kernel space to user space (copy_to_user).
                - write() – Copies data from user space to kernel space (copy_from_user).
                - release() / close() – Cleans up when the file is closed.
                - ioctl() – Handles device-specific configuration and control commands.
            4. struct cdev: The internal kernel structure representing the character device itself, registered via functions like cdev_init() and cdev_add().

        - Basic Development Workflow:
            1. Write the kernel module code defining your file_operations and buffer management.
            2. Register a device number region using alloc_chrdev_region() or register_chrdev_region().
            3. Initialize and add the cdev structure to the kernel.
            4. Build the module using a Makefile and load it into the running kernel via insmod.
            5. Create a device node in /dev and test read/write operations from user space.

	File operations:
        - File operations are the basic actions an operating system performs to manage and manipulate data stored in files and directories.
        - Core Operating System File Operations:
            1. Create: Make a new file or directory on a storage device using system calls like open() / CreateFile() for files or mkdir() / CreateDirectory() for folders.
            2. Open: Load or initialize a file reference into memory so that read or write actions can take place.
            3. Read: Retrieve and access data from a file without changing its contents.
            4. Write: Store, update, or append new data into an existing file.
            5. Seek / Reposition: Move the internal read/write pointer to a specific location or byte offset within a file.
            6. Close: Release the file handle and memory resources after finishing operations to prevent data corruption.
            7. Rename / Move: Change the name or path of a file or directory using commands or APIs like rename() or MoveFile().
            8. Delete / Unlink: Permanently remove a file or directory from secondary storage to free up space.
            9. Truncate: Erase all contents inside a file while keeping its name, attributes, and file handle intact.

	open/read/write/ioctl:
        - open, read, write, and ioctl are fundamental Unix/Linux system calls used to interact with the file system and hardware devices. Under the Unix philosophy where "everything is a file," hardware devices are represented as special files (usually inside /dev/). These system calls serve as the standard user-space interface that bridges programs to kernel-level device drivers.

	Platform drivers:
        - Platform drivers are a special class of device drivers in the Linux kernel used to manage non-discoverable hardware components—such as system-on-chip (SoC) peripherals, UARTs, I2C controllers, and GPIOs—that connect directly to the CPU bus rather than through self-enumerating buses like PCI or USB.

        - Key Concepts:
            - Platform Bus: A virtual bus used by the Linux kernel to connect platform drivers with platform devices.
            - Platform Device (struct platform_device): Represents the physical hardware component, holding a name, ID number, memory addresses, and interrupt request (IRQ) resources.
            - Platform Driver (struct platform_driver): The software code that controls the device, registered with the kernel to handle hardware operations.

        - Core Functions & Structure:
            - probe(): Called when a matching platform device is found; it verifies that the hardware exists, requests resources (like memory or clocks), and initializes the device.
            - remove(): Cleans up and releases resources when the driver or device is unloaded.
            - Power Management: Supports optional callback functions for suspend, resume, and shutdown states.

        - How They Work:
            - Hardware Description: The hardware is described via board files, ACPI, or a Device Tree (DTB) instead of being auto-detected.
            - Registration: The driver registers itself with the platform bus using platform_driver_register().
            - Binding: The kernel matches the device's name or compatible string to the registered driver and executes the driver's probe() function.

	Device Tree matching:
        - Device Tree (DT) matching is the mechanism used by the Linux kernel to bind an operating system device driver to a specific piece of non-discoverable hardware (like a peripheral on an I2C, SPI, or memory-mapped platform bus).
        - Instead of hardcoding hardware initialization details directly into the kernel source, the hardware configuration is externalized into a Device Tree Source (.dts) file. The kernel matches this description against its compiled driver table at runtime.
        - 🔑 The Core Driver-to-Hardware Matchmaker: compatible
            - The DTS Node Entry: Every hardware peripheral defined in a device tree has a compatible property. The format follows a standard convention: "vendor,device-model". Multiple strings can be listed in order of preference (from most specific to most generic).
            - The Kernel Driver Definition: In the kernel driver code, the driver provides an array of IDs using the of_device_id structure.

        1. In the Device Tree (.dts file):
                i2c-sensor@48 {
                    compatible = "acme,supersensor-v2", "acme,supersensor";
                    reg = <0x48>;
                    status = "okay";
                };

        2. In the Kernel Driver Code (.c file):
                static const struct of_device_id my_sensor_of_match[] = {
                    { .compatible = "acme,supersensor-v2" },
                    { .compatible = "acme,supersensor" },
                    { } // Sentinel marking the end of the array
                };
                MODULE_DEVICE_TABLE(of, my_sensor_of_match); // Enables driver autoloading

                static struct platform_driver my_sensor_driver = {
                    .driver = {
                        .name = "acme-supersensor-driver",
                        .of_match_table = my_sensor_of_match, // Enforces the DT matching
                    },
                    .probe = my_sensor_probe,
                    .remove = my_sensor_remove,
                };

        - When the kernel boots and parses the tree, it encounters the node, loops through its compatible strings, and looks for an exact string match inside the of_match_table of registered drivers. If a match succeeds, the driver's .probe() function is executed to initialize the device.

	Probe/remove:
        - In Linux device driver development, probe() initializes a device when Linux binds a driver to it, while remove() cleans up when the device is detached from that driver.
        - probe() — device initialization:
            - The Linux driver core calls probe() when a device matches a registered driver and the required binding conditions are met.
            - Typical operations include:
                    Allocate memory for driver-specific data.
                    Obtain hardware resources from Device Tree.
                    Map memory-mapped registers.
                    Configure GPIOs, clocks, and interrupts.
                    Initialize the hardware.
                    Register a userspace interface if required.
        - remove() — device cleanup:
            - The driver core calls remove() when the device is detached from the driver.
            - Typical operations include:
                    Stop hardware activity.
                    Disable interrupts and cancel pending work.
                    Unregister userspace interfaces.
                    Release resources that are not automatically managed.
                    Leave the hardware in a safe state.

                    - EDO DRAM
                    - BEDO DRAM
                    - SDRAM
                    - DDR SDRAM
                    - DDR2 SDRAM

                    - DDR4 SDRAM
                    - DDR5 SDRAM
            - LPDDR (Low Power DDR)

                    - LPDDR2
                    - LPDDR3
                    - LPDDR4
                    - LPDDR4X
                    - LPDDR5
                    - LPDDR5X
                    - LPDDR6
            - Graphics Memory
                    - VRAM
                    - SGRAM
                    - WRAM
                    - GDDR2
                    - GDDR3
                    - GDDR4
                    - GDDR5
                    - GDDR5X
                    - GDDR6
                    - GDDR6X
            - High Bandwidth Memory
                    - HBM
                    - HBM2
                    - HBM2E
                    - HBM3
                    - HBM3E
    - SRAM – Static RAM
            - Asynchronous SRAM
            - Synchronous SRAM
            - Pipeline Burst SRAM
            - QDR SRAM
            - DDR SRAM
            - PSRAM

    - CPU Internal Volatile Memory
            - Registers
                    - General Purpose Registers

            - CAM – Content Addressable Memory
            - TCAM – Ternary Content Addressable Memory
